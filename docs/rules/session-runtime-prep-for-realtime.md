# Session Runtime Prep For Realtime

## 1. Purpose

This step prepares the match session layer for Phase 20.1 realtime sync without implementing the websocket server yet. The goal is to make the authoritative runtime contract explicit: clients submit participant commands, the session owns canonical state, rules-core applies gameplay, and clients receive player-specific projections.

## 2. Why local runtime needed an authoritative transport-facing model

The local prototype already used `match-session` as a strong in-memory authority, but the callable surface was still closer to an internal room command API than a realtime client protocol. Phase 20 needs a transport-safe boundary before networking arrives, especially around hidden information, stale clients, history ordering, and system-only actions.

## 3. Chosen transport baseline

The transport-facing runtime primitive originally targeted bidirectional pushes. The Phase 20 transport decision now uses `server_route_commands_with_projected_snapshots` as the first canonical baseline, with this runtime contract sitting behind the server route.

Clients send participant commands to the server/session authority. After accepted commands, the server returns or makes available full projected snapshots per participant, plus accepted history entry ids for reconciliation. Full projections are intentionally preferred first over fine-grained deltas because they are simpler, hidden-information safe, and reconnect friendly.

## 4. Command contract

`RealtimeClientCommand` contains:

- `commandId`
- `roomId`
- `participantId`
- optional `expectedRoomRevision`
- `payload`

The payload is an engine command, but the realtime boundary only accepts participant-owned commands. System actions are rejected before they reach `submitMatchRoomCommand`. Player actions and choice responses are still validated against the authoritative participant-to-player binding in the room.

## 5. Server/session response and projected push model

`submitRealtimeClientCommand` returns one of:

- `accepted`: updated serializable session document, room result, accepted history entries, and projected pushes.
- `invalid`: unchanged or explicitly failed document, structured code/message, and no pushes.
- `blocked`: unchanged document, blocking request information, and no pushes.

`RealtimeProjectedStatePush` carries a full `ProjectedMatchRoomForParticipant`, the room and engine revisions, push reason, and accepted history entry ids. The push never exposes raw canonical state.

## 6. Role of snapshot/history

Persistence remains `snapshot+event-history`. No broad persistence rewrite was needed: the existing model already stores canonical room snapshots and appends accepted engine events only. This step makes that model load-bearing for realtime by recording accepted command results before projected pushes are produced.

Rejected and blocked client commands do not append history entries.

## 7. System actions vs client actions

Clients cannot submit system actions through the realtime contract. Lifecycle actions, mandatory flow, trigger followups, cleanup, and other system-owned transitions must be generated by session/runtime authority, not by transport consumers.

The lower-level `submitMatchRoomCommand` still supports system sources for local/session-owned automation. The realtime client wrapper always submits through a participant source and rejects system action payloads first.

## 8. Relationship to hidden-information and availability contracts

Realtime pushes use the existing hidden-information projection layer. One canonical room revision can produce different projected payloads per participant. Availability and pending request state remain inside the projected state, so clients can render legal choices without receiving god-view state.

Stale room revisions, wrong participants, closed rooms, blocked pending-request states, and projection failures are structured outcomes rather than silent fallbacks.

## 9. What is intentionally NOT implemented yet

This step does not implement the websocket server, room presence protocol, delta compression, optimistic reconciliation, reconnect replay, distributed persistence, or production multiplayer orchestration. It also does not move gameplay logic into transport code.

## 10. Summary

The session layer now has a real transport-facing runtime contract. Canonical state remains session-owned, clients submit participant commands only, accepted commands append accepted history, and every accepted update can produce participant-specific projected snapshots for realtime consumers.
